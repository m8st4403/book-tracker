## 開発・リリース

通常確認：

```bash
npm test
```

最終配布判定：

```bash
npm run test:release
```

`test:release` は品質テストに加えて、GitHubアップロードフォルダの内容、履歴資料の混入、バージョン整合性、必要な品質資産、ZIPの2階層構造を検査します。

## GitHubアップロードの運用

GitHubにアップロードするときは、**既存のGitHubアップロードフォルダの中身を削除してから、次のバージョンの `GitHubアップロード` フォルダ一式だけをアップロード**します。

`アップロード不要` は、CHANGELOG・過去監査・旧マトリクス・調査資料などの保管場所です。通常のGitHubアップロードには含めません。

現在のGitHubアップロード側には、現行版の実装と、それを検査するために必要なファイルだけを置きます。履歴資料を毎版コピーして累積させません。

## 重要な品質方針

新しい不具合が見つかった場合も、「不具合1件につきテスト1件」を追加することを第一選択にしません。

1. 共通不変条件として説明できるか
2. 独立Oracle/Propertyへ昇格できるか
3. Mutationで故障検出能力を確認できるか
4. 必要な代表E2Eだけを追加するか

の順に判断します。

これにより、過去の修正が継ぎ接ぎとして増殖することを防ぎます。

## v4.13.230 品質資産台帳の一本化
- `RELEASE_ASSET_MANIFEST.json` をGitHubアップロード対象ファイルの正本とし、Release Artifact Guardのハードコードされた許可リストを廃止。
- 新しい検査・診断・計測ファイルを追加した場合、台帳と実ファイルの不一致を配布前に検出する。
- 検査を増やすこと自体を目的にせず、既存の共通契約・Oracle・Mutation・E2Eへ接続できない資産はRelease対象にしない。

## v4.13.230 Runtime実行環境の切り分け
実ブラウザE2Eは、アプリの検査結果とブラウザ実行環境の可用性を分離して扱う。`npm run test:runtime-env` は Chromium の起動可否だけを確認し、環境側で完走できない場合は `UNAVAILABLE` として扱う。これはアプリ機能のPASSを意味しない。
